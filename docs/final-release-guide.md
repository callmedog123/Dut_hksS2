## P0-1：真实 Chrome 三平台手动验收

**为什么必须做**：目前所有测试都是 Node.js 模拟环境跑的，从来没有在真实 Chrome 里打开过这个扩展。自动测试测的是"逻辑对不对"，测不出"Chrome 实际加载会不会报错""真实网页的 DOM 结构和我们猜的是否一致"。

### 第一步：把扩展加载进 Chrome

1. 打开 Chrome，地址栏输入 `chrome://extensions/` 回车。
2. 打开右上角的"开发者模式"开关（没打开的话看不到"加载已解压的扩展程序"按钮）。
3. 点击"加载已解压的扩展程序"。
4. 选择这个仓库的根目录（就是 `manifest.json` 所在的那个文件夹，**不要**选进某个子文件夹）。
5. 加载成功后，会出现一张扩展卡片，名字是"The Unclicked（余路）"。

**怎么判断通过**：
- 卡片上没有红色的"错误"按钮。如果有，点开看报错内容，通常是路径或语法问题。
- 点击卡片上的"详情"，确认权限里只有：`sidePanel`、访问 `search.bilibili.com`，以及知乎/抖音的精确搜索页脚本注入。**不应该**看到 `<all_urls>`、Cookie、tabs 之类的权限。

### 第二步：按检查表逐项操作

打开 `docs/manual-browser-checklist.md`，这份表已经把要测的内容拆成了 A 到 I 九个部分。你不需要自己想测什么，照着打勾就行：

| 部分 | 测什么 | 大概耗时 |
|---|---|---|
| A. 干净安装 | 上面第一步做的事，正式记录一下 | 5 分钟 |
| B. 本地 Demo 完整闭环 | 不需要联网，用扩展自带的 Demo 页面测三轮完整流程 | 15 分钟 |
| C. 数据控制 | 暂停/恢复采集、单条删除、清空全部数据 | 15 分钟 |
| D. Bilibili 真实搜索页 | 真实打开 `search.bilibili.com` 搜点什么，测采集是否正常 | 20 分钟 |
| E. 知乎真实搜索页 | 需要你自己在 Chrome 登录一次知乎账号 | 20 分钟 |
| F. 抖音真实搜索页 | 用不需要登录的公开搜索页 | 20 分钟 |
| G. Service Worker 恢复 | 模拟浏览器崩溃/重启后数据是否还在 | 10 分钟 |
| H. 录屏脚本 | 这是给你录视频用的台词稿，先跳过，等要录视频时再看 | - |
| I. 发布签字 | 最后汇总确认 | 5 分钟 |

**建议做法**：

1. 先做 B（本地 Demo），因为不需要联网、不需要登录任何账号，最简单，用来验证扩展本身没坏。
2. 再做 C（暂停/删除/清空），确认数据管理功能正常。
3. 然后做 D（Bilibili），因为它权限最少、最容易测。
4. 最后做 E（知乎）和 F（抖音）——这两个需要真实登录/公开搜索，也是最可能因为网站改版导致选择器失效的地方。
5. G 建议单独留出 10 分钟，因为它涉及在 `chrome://extensions/` 里手动停止 Service Worker，操作稍微特殊。

**遇到问题怎么办**：

- 如果 D/E/F 某个平台的候选项完全不出现（比如 Bilibili 搜索页明明有视频卡片，但 Side Panel 一直显示"0 个候选项"），大概率是网站改版导致选择器失效了。这种情况先截图 + 记录当前 URL + 打开 F12 控制台看有没有报错，然后告诉我，我可以帮你诊断具体是哪个选择器失效了（但我没法自己打开 Chrome 去验证，需要你提供截图或 DOM 结构）。
- 每测完一个部分，在检查表对应的 `[ ]` 前面加上 `[x]`，方便追踪进度，这个文件是纯文本，用任何编辑器改都行。

**怎么判断整体通过**：九个部分都打勾、Console 没有出现红色报错、B 部分的三轮表格全部通过。

## P0-2：处理"开发起点证明"截图隐私风险

**背景**：仓库里有个文件夹 `开发起点证明/`，里面 5 张截图是用来证明项目开发时间线的比赛材料。我已经打开逐张看过，**没有发现明文密码或密钥**，但有两类信息你需要自己判断是否要处理：

1. 截图里如果出现了终端窗口或文件管理器窗口，可能会带出你电脑上的**用户名**或**文件夹路径**（比如 Windows 系统盘下用户目录那一类路径）；
2. 截图里如果有 GitHub 提交历史页面，会显示你的**真实 GitHub 账号名**。

### 怎么检查

1. 用系统自带的图片查看器依次打开这 5 个文件（在文件管理器里进入 `开发起点证明` 文件夹）：
   - `01_主证明_2026-08-21_仓库首次提交与初始文件状态.png`
   - `02_补充证明_2026-08-23_GitHub提交历史与中期文档记录.png`
   - `03_可选进度_2026-08-23_静态原型_未选择路径与情境化重逢.png`
   - `04_可选进度_2026-08-23_静态原型_打开操作反馈.png`
   - `05_可选进度_2026-08-23_静态原型_删除操作反馈.png`
2. 重点看每张图的边框、标题栏、地址栏区域——这些地方最容易带出路径或账号名。
3. 问自己两个问题：
   - 这张图暴露的用户名/账号名，是我不介意公开的吗？（很多人本来就用真名或已知的 GitHub 账号做开源项目，这种情况不需要处理）
   - 这张图有没有暴露我完全不想让人知道的信息（比如公司内部路径、其他项目名称）？

### 三种处理方式，按你的判断选一种

**方式 A：不处理**（如果内容都能接受公开）
不用做任何事，直接跳过这一节。

**方式 B：局部打码后替换**（如果只是某一小块区域需要遮住）

1. 用画图工具（Windows 自带"画图"或"截图工具"）打开对应图片；
2. 在需要遮盖的区域画一个实心矩形盖住；
3. 另存为同名文件，覆盖原文件；
4. 在这个仓库里执行：

```powershell
git add "开发起点证明/文件名.png"
git commit -m "为开发起点证明截图打码敏感信息"
```

**方式 C：整个文件夹从仓库移除**（如果觉得这些截图不重要，比赛不强制要求就不留了）

```powershell
git rm -r "开发起点证明"
git commit -m "移除开发起点证明材料"
```

> 注意：这只是让**以后**的提交里不再包含这些文件。如果你的 GitHub 仓库历史记录是公开的，这些图片在**旧的 commit 里依然能被人翻出来**。如果你要求"完全抹除历史痕迹"，需要用 `git filter-repo` 这类工具重写历史，这是一个更复杂、有风险的操作（会改变所有 commit 的哈希值），一般比赛材料不需要做到这个程度。如果你确实需要，请单独告诉我，我会更谨慎地带你走一遍流程并提前确认。

## 决策：`.opencode/opencode.json` 是否移出仓库

**这是什么文件**：这是你使用的 AI 编程助手工具（就是我）的个人配置文件，里面记录了你配的模型和调用地址。

**检查结果**：里面的 `apiKey` 字段写的是 `{env:OPENAI_NEXT_API_KEY}`，这是一个**占位符**，表示"实际密钥从环境变量读取"，文件本身**不包含明文密钥**。但文件里的 `baseURL: https://api.openai-next.com/v1` 会暴露你使用的是哪个第三方 AI 中转服务。

**这不是运行时代码**，跟扩展能不能用、比赛评审看不看代码完全无关，纯粹是"要不要让外人知道你用了这个工具配置"的个人选择。

### 如果你想移出仓库

```powershell
git rm .opencode/opencode.json
git commit -m "移除个人 AI 工具配置"
```

如果以后还想在本地继续用这个配置（只是不上传到 GitHub），可以把它加进 `.gitignore`：

```powershell
Add-Content -Path .gitignore -Value ".opencode/opencode.json"
```

### 如果你觉得没关系，可以留着

不用做任何事。这是个人偏好问题，不是安全漏洞。

## P0-3：审查并提交当前工作区改动

**现状**：这次修复涉及 19 个文件的改动，目前都还"浮"在你的电脑上，没有生成正式的提交（commit）。这是我特意留给你的——按规则，AI 不能代你做 commit 决定。

### 第一步：看看到底改了什么

```powershell
git status --short --branch
```

这会列出所有改动的文件。想看具体改了哪些内容：

```powershell
git diff background/consideration.js
```

把文件名换成你想看的任意一个。如果想一次看全部改动（内容会很长）：

```powershell
git diff > 改动内容.txt
```

然后用文本编辑器打开 `改动内容.txt` 慢慢看。

**你在看什么**：确认这些改动都是你（或我）预期要做的修复，没有意外改到不相关的地方。凡是行首带 `+` 的是新增内容，带 `-` 的是删除内容。

### 第二步：确认没问题后提交

```powershell
git add -A
git commit -m "修复任务9-17验收发现的接线问题：标签评分接线、暂停恢复、抖音caps对齐"
```

`git add -A` 会把所有改动（包括修改、新增文件）都加入这次提交。如果你想更精细地分批提交，可以用 `git add 文件名` 一个一个加。

### 第三步：推送到 GitHub

```powershell
git push origin codex/tasks-9-12-safe
```

这一步会把提交上传到 GitHub 上的 `codex/tasks-9-12-safe` 分支（不是 `main`，`main` 还是旧版本，这是故意的，见下一节）。

## 合并到 main 分支

**为什么不能直接改 main**：`main` 分支目前还是旧版本代码。为了避免"改坏了没法恢复"，规范做法是先在别的分支（也就是现在的 `codex/tasks-9-12-safe`）改好、测好，再正式合并进 `main`。

### 推荐方式：通过 Pull Request（网页操作，最安全）

1. 完成上一节的 `git push` 之后，打开浏览器访问：
   `https://github.com/callmedog123/Dut_hksS2`
2. 页面上应该会出现一个黄色提示条"Compare & pull request"，点它。如果没有，点击顶部的"Pull requests"标签，再点"New pull request"。
3. 确认左边基准分支是 `main`，右边是 `codex/tasks-9-12-safe`。
4. 填写标题（比如"完成任务9-17修复与最终验收"），描述里可以简单写做了什么。
5. 点击"Create pull request"。
6. 这个页面会自动显示所有改动的文件对比（Files changed 标签），你可以在网页上再看一遍。
7. 确认没问题后，点击"Merge pull request" → "Confirm merge"。

**这样做的好处**：GitHub 会自动检查有没有冲突，合并记录会永久保留在历史里，比直接在本地合并更安全、更容易追溯。

### 如果你更习惯命令行

```powershell
git checkout main
git pull origin main
git merge codex/tasks-9-12-safe
git push origin main
```

**执行前请确认**：`git status` 显示工作区是干净的（没有未提交改动），否则先完成上一节的提交。

## 从空目录重新 clone 验证发布候选版本

**为什么要这么做**：你现在这个工作目录里可能残留了一些临时文件、缓存或者本地专属的配置，直接拿这个目录去提交容易"意外带了本机才有的东西"。重新 clone 一份全新的、干净的副本，能验证"仅凭 GitHub 上的内容"就能正常跑起来。

### 操作步骤

1. 找一个新的空文件夹，比如桌面上新建一个 `test-clone`（把下面的 `<你的桌面路径>` 换成你自己的桌面完整路径，或者换成任意其他空目录）：

```powershell
cd <你的桌面路径>
New-Item -ItemType Directory -Path "test-clone"
cd test-clone
```

2. 克隆仓库（确保已经完成上一节的合并，main 分支是最新的）：

```powershell
git clone https://github.com/callmedog123/Dut_hksS2.git
cd Dut_hksS2
```

3. 跑一遍测试和构建检查：

```powershell
npm test
npm run typecheck
npm run build
```

**怎么判断通过**：三个命令都显示"通过"，没有红色报错，测试数量应该是 496/496（除非你合并时又改了代码）。

4. 顺便在这个干净的目录里，把"P0-1 真实 Chrome 手动验收"的第一步（加载扩展）重新做一次，确认从 GitHub 上下载下来的代码本身可以正常加载。

5. 验证完之后，这个 `test-clone` 文件夹可以直接删掉，它只是用来验证的临时副本：

```powershell
cd <你的桌面路径>
Remove-Item -Recurse -Force test-clone
```
